# 实时推理界面

项目提供类似 Gradio 的轻量 Web 页面，使用 Python 标准库 HTTP 服务，不需要安装 Gradio。白底、细分隔线，包含 Prompt/seed/尺寸/采样配置、执行计划、任务取消、阶段耗时、GPU 前向时间与视频预览。

## 不加载模型，先试界面

```bash
vidinfer serve --demo --workspace ./runtime/ui-demo --port 7860
```

打开 `http://127.0.0.1:7860/`。演示模式使用模拟进度与时间，并明确标识，不能当作 H3 性能数据。

## 在自己的 GPU 机器上运行

准备 README 要求的 Linux/CUDA 环境、完整模型权重及 ffmpeg，然后执行：

```bash
vidinfer serve \
  --checkpoint /mnt/nas/models/MiniMax-H3 \
  --workspace /mnt/nas/vidinfer \
  --port 7860
```

HTTP 服务启动时不加载模型。首次提交才建立 H3Session，后续请求复用同一个 Session 的模型与组件。可通过 `--text-cache /mnt/nas/captures/text_condition.pt` 传入已有兼容文本条件；普通新 prompt 会走文本编码流程，首次编码器加载和磁盘卸载可能较慢。

当前仍只验证单张 H20/BF16，普通小显存显卡无法直接按默认配置跑完整 H3。示例初始选 5 点采样用于快速诊断，可切换 29 点；帧数、分辨率和 Token 预算遵循原推理接口的检查。

远程机器只绑定 loopback。在自己的电脑建立 SSH 隧道：

```bash
ssh -N -p 22 -L 7860:127.0.0.1:7860 user@gpu-host
```

再打开本机 `http://127.0.0.1:7860/`。这是研发界面，没有公开服务的用户鉴权/配额能力；不支持直接绑定 `0.0.0.0`。

## 复用已有 H20 resident worker

当前调试机使用 `--resident-config`，HTTP 进程只管理请求文件，不持有 GPU 模型。请求通过已有串行队列进入原工作进程，在同一进程使用 `H3Session.from_model()` 借用 DiT，并缓存 Session。没有重新启动工作进程或加载第二份 DiT。

```bash
vidinfer serve \
  --resident-config /mnt/nas/project/ui-resident.json \
  --workspace /mnt/nas/vidinfer \
  --port 7860
```

配置格式见 `tools/web/resident-config.example.json`。此适配器专用于旧 NAS worker 的 `qk_abba` 热加载协议，要求该 worker 已接入 `runner='web'` 分发，在同一进程调用 `vidinfer.web.resident.main(args, model, resident)`。仅复制配置不会自动改造任意第三方 worker；其他机器应先用上一节独立模式。

文本/解码组件会随借用 Session 留在工作进程中供后续请求复用。关闭 HTTP 页面或 HTTP 服务不会卸载原 DiT，也不等于释放该 worker 缓存的组件；做其他大显存实验前应协调同卡使用。不要在运行中热改或清理 worker 模块。

## 页面上各个时间代表什么

- 排队：HTTP 接收任务到工作器开始处理之间的等待，不等于内部 Engine 的短队列时间。
- 准备/加载：独立模式包含模型首次加载；常驻模式只准备 Session 与执行计划。
- 文本条件：缓存命中可能非常短；加载编码器/真正文本编码会作为子阶段显示。
- 去噪：完整采样循环边界等待当前 Stream 完成，Wall 截止到设备完成；不会在每个 DiT 前向同步。
- GPU 前向：查询 post hook 已记录的 CUDA Event，只有完成后才读取 elapsed time。`steps_done` 是 CPU 返回次数，页面进度条用的是 GPU 已完成次数。
- 解码器加载、VAE 解码、回传整理和音视频导出分别记录。子阶段包含在父阶段中，不能相加。

页面约每秒刷新一次，worker 约每 0.25 秒发布快照。这是实时运行诊断，轮询与阶段边界等待会带来观察开销，正式性能对比仍使用 `experiment` 工具。

GPU 前向进度到 100% 后仍可能加载解码器、解码和导出，不代表视频已经就绪。首次组件加载尤其应观察当前阶段，而不是把所有等待都算成 GPU Kernel 执行。

## 取消、状态与产物

最多保留两个排队或运行任务。取消是协作式请求，在安全阶段/前向边界响应；已经提交的 CUDA 工作不会被撤回，较长的组件加载也不会被强制打断。设备清理尚未确认时显示取消处理中/等待完成，不提前显示资源已释放。

刷新页面后可从最近任务恢复查看。关闭标签页不会取消任务。界面状态保存在 `workspace/web/jobs/`，模型产物仍在 `workspace/outputs/`，原有请求记录仍在 `workspace/requests/`。

视频预览和下载只访问任务记录的 MP4/WAV，并检查路径在 workspace 输出根内；支持 HTTP byte-range。服务限制 Host、同源写请求、临时请求 token、请求大小和参数集合，不提供任意文件浏览或执行入口。

新增代码入口：`web/server.py`、`web/backend.py`、`web/progress.py`、`web/resident.py`。`RequestContext.stage()` 记录可并发读取的阶段历史，`RequestHandle.status()` 提供状态快照；它们不依赖 Torch。

## 本次验证（2026-11-14）

安装包 51 项回归通过。H20 通过界面后端实际生成 960×544、124 帧的音视频：首次约 326 秒，其中解码器首次加载约 274 秒、去噪约 38 秒、解码约 11 秒；复用 Session 的下一次约 50 秒，没有重复加载解码器。两次固定 seed 的音视频 latent 与历史基准逐字节一致。这是一组冷/热状态诊断，不是正式加速比实验。

已验证排队取消、非阻塞 Event 进度、视频格式与 HTTP 206 分段读取。latent 输出选项用于计时与哈希验证，Web 结果不导出 Tensor 文件。当前桌面自动化返回权限拒绝，未完成这一版的浏览器视觉验收；静态脚本语法、DOM 选择器与真实接口链路已检查。
