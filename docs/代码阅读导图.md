## 先读哪些文件

1. `types.py`：`PreparedModel` 是共享模型，`ExecutionPlan` 是复用计划，`RequestContext` 是一次请求的可变状态。
2. `session.py`：看 `from_pretrained()` 如何准备模型，以及 `generate()` 如何调用 `submit().wait()`。
3. `engine.py`：先看 `submit()`，再看 `_execute()`。把排队、设备提交、完成等待与资源清理分清。
4. `models/h3.py`：先跳到 `class H3Adapter`，按 `adopt → validate → prepare_plan → execute → finalize` 读。
5. `stages.py`：看文本缓存键、组件复用、GPU/CPU/磁盘放置，以及解码为什么放在 execute 内。
6. `registry.py` 与 `backends/cuda.py`：追踪模型需要的算子如何变成真实实现。
7. `kernels/qk_norm_rope.py → .cpp → .cu`：沿 Python 包装、C++ 绑定、CPU 启动入口一路追到 GPU 线程。

第一次可以跳过 `loading/adaln.py` 的缓存构建细节，先读它的 Router 和 CachedProjection，理解预计算表如何按时间步被选中。

## 一次请求的调用链

```text
H3Session.submit(prompt)
  → 构造 DenoiseRequest
  → Engine.submit()
      → 校验参数、检查容量、取得计划、创建 RequestContext
      → 后台线程执行 Engine._execute()
          → 取得模型执行锁、Backend.activate()
          → H3Adapter.execute()
              → H3Stages.encode()：缓存命中或官方文本编码
              → 每请求新建采样器/状态/RNG
              → 官方去噪 Pipeline
                  → Transformer Block
                      → H3AttentionProcessor
                          → 注册表选出的 QK 与 Attention 实现
                      → FusedSwiGLU（若计划启用）
              → H3Stages.decode()（若请求视频）
          → 记录并等待 GPU 完成事件
          → H3Adapter.finalize()：CPU latent、哈希、媒体导出
          → 清理请求引用
  → RequestHandle.wait() 返回结果或抛出异常
```

GPU 解码位于 `execute()` 内，保证 Engine 的最终事件覆盖去噪和解码的所有设备工作。
`finalize()` 在完成确认后做 CPU 输出整理和 ffmpeg 导出。

## 为什么分开共享状态与请求状态

| 对象 | 生命周期与所有权 |
|---|---|
| DiT 权重 | Session 持有并跨请求复用；借用时外部模型拥有者也继续持有 |
| 模型计划 | 模块树、processor、Router 独立；参数和 buffer Tensor 的存储共享 |
| 文本编码器/VAE | Stage 对象持有，在 Session 内复用 |
| 采样器/RNG/事件/中间 latent | 每个请求独立 |
| 输出 CPU latent 与路径 | 由返回结果和调用者持有 |

`retain()` 增加引用，不复制权重。`release()` 清理临时引用，不等于清空显存缓存。
调用者若继续持有 plan 或 handle，模型视图仍可能活着；`close()` 不会强行销毁调用者仍持有的对象。

## Python 与 CUDA 的边界

```text
H3AttentionProcessor：self.qk.run(...)
  → CUDABackend 注册的 fused_qk(...)
  → extension().forward(...)
  → .cpp：module.def("forward", &h3_qk_norm_rope_cuda)
  → .cu：h3_qk_norm_rope_cuda() 在 CPU 上检查参数并取得显存地址
  → kernel<<<grid, threads, 0, current_stream>>>()
  → __global__ 函数由 GPU 线程执行
```

QK Kernel 中一个 Warp 负责一个 Token/Head 的 128 个通道，一个 lane 负责 4 个通道。
Warp 归约得到 RMS，再通过 shuffle 读取 RoPE 配对通道。归一化中间值保留 BF16 舍入语义并继续参与 RoPE，减少显存中间写回。

## 容易混淆的完成状态

- Python forward 返回：有关操作可能仅仅提交给 GPU。
- `CUDACompletion.ready()`：特定 GPU 事件是否已完成。
- `RequestHandle.ready()`：整个后台请求是否结束；此时也可能是失败或取消。
- `wait(timeout)` 超时：后台任务仍可能运行，不会自动释放它的资源。

取消发生后仍要等已经提交的工作完成。若连完成确认也失败，Engine 保留资源引用并拒绝继续执行，交给进程级故障处理。

## 从测试反向理解

`tests/test_core.py` 用替身控制后台线程，验证取消、超时、背压、错误隔离与引用释放，不执行模型。
`tests/test_runtime.py` 检查输入预算、路径和缓存位置。
`tests/test_media.py` 使用微型数组和真实 ffmpeg 验证音视频产物，不占用 GPU。
真实 H3 数值与媒体回归独立记录，不把 CPU 替身测试当成 GPU 正确性证据。
